Upgrading a project from ferrovue 0.11 to 0.12: the steps to take and what behaves differently.

The [CHANGELOG](https://github.com/Kinsmir/ferrovue/blob/main/CHANGELOG.md) lists every change;
this page picks out what an application notices. Most of it is one change: every item of the crates
and of the npm package is named at the module or entry that defines it, and nothing is lifted to a
root above it. Steps 3 and 4 cover that change, with a table of every path that moved. The other
changes of 0.12 to unions of string literals have sections of their own, steps 5 and 6 and
[Behaviour that changed](#behaviour-that-changed). The page for the release before is
[`upgrading_to_0_11`](crate::guide::upgrading_to_0_11).

# Steps

## 1. Bump both halves together

The npm package and the crates are released together at one version, and generated code works with
the crate of its own release. Bump the npm package:

```sh
pnpm add -D ferrovue@^0.12.0
```

and the crate, in `Cargo.toml`:

```toml
ferrovue = "0.12"
```

`ferrovue` depends on `ferrovue-core`, `ferrovue-router` and `ferrovue-i18n` at exactly its own
version, so an application that names only `ferrovue` gets the other three with it. One that names
any of them itself bumps it to 0.12 as well.

## 2. Generate every component again

```sh
pnpm ferrovue
```

The 0.12 compiler writes version 6 of generated code, and `mod.rs` opens with
`ferrovue::__compat!(6)`. Version 6 reads the literal of every union's enum through
[`Union`](crate::props::Union), which the 0.11 crate lacks, and names every item of the crates at
the module that defines it: `fv::html::Html`, `fv::render::Refused`, `fv::router::Route`,
`fv::core::escape_into`. The 0.12 crate no longer has the paths earlier versions call, so it
supports version 6 alone, and stops a module generated by 0.11 at its first line:

```text
error: this module was generated as version 5 of ferrovue's generated code, and this `ferrovue` crate supports version 6: use the `ferrovue` npm package and the `ferrovue` crate of one release, and run `ferrovue` to generate the module again
```

The 0.11 crate supports versions 2 to 5, and stops a module of version 6 the same way. Every
generated file changes once. A CI job that runs `pnpm ferrovue --check` reports each module as
stale until it is generated again with 0.12 and committed. See
[the version check](crate::guide::generated_code#the-version-check).

and [`i18n`](crate::i18n), whole: `ferrovue::Router` is
[`ferrovue::router::Router`](crate::router::Router), `ferrovue::escape_into` is

module before and keeps every path below it (`ferrovue::i18n::Args`); `ferrovue::I18n` is
[`ferrovue::i18n::I18n`](crate::i18n::I18n).

```rust
use ferrovue::core::escape_into;
use ferrovue::props::Record;
use ferrovue::router::Router;

// 0.11: ferrovue::Router, ferrovue::escape_into and ferrovue::Record.
let router = Router::new(&["/", "/books/:id"]);
assert_eq!(router.at("/books/dune").param("id"), Some("dune"));

let mut out = String::new();
escape_into(&mut out, "Tom & Jerry");
assert_eq!(out, "Tom &amp; Jerry");

let scores: Record<'_, i64> = [("b", 1), ("10", 2)].into_iter().collect();
assert_eq!(scores.keys().collect::<Vec<_>>(), ["10", "b"]);
```

`ferrovue-core`, `ferrovue-router` and `ferrovue-i18n` define their items at their roots, so an
application that names one of them itself keeps its paths (`ferrovue_core::escape_into`).

`ferrovue::core` is the `ferrovue-core` crate. A module that imports it by name, or every module
of `ferrovue` with `use ferrovue::*;`, has the name `core` bound to it, which hides Rust's own `core`
crate from paths written in that module: write `::core::mem::swap` there, with the leading `::`.
Generated code and a module that names `ferrovue::core::…` in full are not affected.

The configuration names Rust types by their paths too. Where `ferrovue.config.json` names one of
the crate's, it names the new path:

| Key | 0.11 | 0.12 |
|---|---|---|
| `dateType` | `ferrovue::JsDate`, the default | `ferrovue::date::JsDate`, the default |
| `trustedHtml` | `ferrovue::BasicHtml`, `ferrovue::InlineHtml`, `ferrovue::Sanitised` | `ferrovue::html::BasicHtml`, `ferrovue::html::InlineHtml`, `ferrovue::html::Sanitised` |

A key that leaves its default needs no change. A type of the application's own that implements
[`JsTime`](crate::date::JsTime), [`TrustedHtml`](crate::html::TrustedHtml) or
[`Union`](crate::props::Union) names the trait at its module in its `impl`.

## 4. Import the npm package's items from their entries

Each entry of the npm package exports only what its own file defines. The items an entry gathered
from other files are exported by the entry that defines them, some of them new:

| 0.11 | 0.12 |
|---|---|
| everything from `ferrovue/client` | `ferrovue`, which exports the same items, `clearLoads` among them |
| `Float`, `InlineHtml`, `TrustedHtml` from `ferrovue` | `ferrovue/types`, as components import them |
| `CONFIG_FILE`, `loadConfig`, `TYPES_MODULE`, `Config`, `HelperSpec`, `RoutesSource`, `ScopeIdMode`, `TwinSpec`, `TypeName` from `ferrovue/compiler` | `ferrovue/compiler/config` |
| `GenError`, `GenErrors`, `SourceLocation`, `ERRORS`, `ErrorCode`, `ErrorDoc`, `docsUrl` from `ferrovue/compiler` | `ferrovue/compiler/errors` |
| `attachSsrRender` from `ferrovue/testing` | `ferrovue/testing/ssr` |
| `fixtureApp`, `readFixture`, `Fixture`, `RouterOptions`, `hydrateRecordedPage`, `renderRecordedPage`, `RecordedPage` from `ferrovue/testing` | `ferrovue/testing/browser` |
| `IslandComponent`, `MountOptions`, `PageOptions`, `PagePart`, `PageRecord`, `RenderPageOptions` from `ferrovue/testing` | `ferrovue` |
| `routeRecords`, `RouteEntry` from `ferrovue/link-router` or `ferrovue/testing`, and `RouteEntry` from `ferrovue/routes` | `ferrovue/route-records` |

The rest stay where they were: the browser API in `ferrovue`; `generate`, `write`,
`isGenerated`, `Alias`, `ResolveOptions`, `Written` and `VERSION` in `ferrovue/compiler`;
`conformanceSuite` and `ConformanceOptions` in `ferrovue/testing`; `linkRouter` and
`LinkRouterOptions` in `ferrovue/link-router`; and `ferrovue/types`, `ferrovue/islands`,
`ferrovue/routes`, `ferrovue/vite` and `ferrovue/volar`, whose items they define.

```ts
// 0.11
import { ClientOnly } from "ferrovue/client";
import { fixtureApp, hydrateRecordedPage, readFixture } from "ferrovue/testing";
import { linkRouter, routeRecords } from "ferrovue/link-router";

// 0.12
import { ClientOnly } from "ferrovue";
import { fixtureApp, hydrateRecordedPage, readFixture } from "ferrovue/testing/browser";
import { linkRouter } from "ferrovue/link-router";
import { routeRecords } from "ferrovue/route-records";
```

`ferrovue/testing/browser` and `ferrovue/route-records` load no module of Node, so a test that
runs in a browser imports them as the conformance suite's browser tests do.

The compiler reads `<ClientOnly>` and `defineLoader` from `ferrovue` alone. A component that still
imports them from `ferrovue/client` is refused where it uses them: `<ClientOnly>` as a child
component that is not one of the project's, and a loader's `await` as a call that is not a
loader's.

## 5. Build lists of a union from the enum

A prop or an interface's field typed as a list of a union of string literals (`tones: Tone[]`) is a
list of the union's enum: `Vec<Tone>`, `Option<Vec<Tone>>` when it is optional or nullable, and
`Vec<Option<Tone>>` for `(Tone | null)[]`. 0.11 made it a list of strings. Its constructor
argument or setter takes `impl IntoIterator<Item = Tone>`, so `vec!["warm".into()]` becomes
`[Tone::Warm]`, and a list of strings from a request is parsed into the enum first. The JSON of an
island and of a page's record are unchanged. A string that the Rust caller holds where the render
needs the union's enum (a value of a `Record<string, Tone>`, a store's state, a prop of a single
literal) is parsed as the component renders, and one outside the union refuses the render with
[FV0518](crate::guide::error_codes#fv0518).

## 6. Name the application's own enums for unions, where it has them

`unions` in `ferrovue.config.json` names an enum of the application's own for a union's `type`
alias, which then takes the place of the enum the compiler generates for it. The enum implements
the new trait [`Union`](crate::props::Union) and has a variant of the name ferrovue would generate
for each literal. A project that leaves `unions` out has nothing to change. See
[Unions mapped to existing enums](crate::guide::props#unions-mapped-to-existing-enums).

## 7. Error codes your CI matches

These sources compiled with 0.11 and are refused with 0.12:

| Source | 0.12 |
|---|---|
| a `computed`, a `ref` or a constant of setup annotated as a union of string literals whose body may give another string, read where a child's prop or an object literal's field takes the union | FV0111 |
| a lookup table whose values are members of a union, holding a value outside it | FV0228 |

And these are new, for `unions`: FV0329 (an entry for an alias that is not a union of two or more
string literals), FV0330 (two unions of the entry's name with other members), FV1119 (a path that
is not one of a Rust type) and FV1120 (an entry no prop or field is typed with).

# Behaviour that changed

## A `ref` of a union holds its enum

A `ref` typed as a union of string literals (`ref<Choice>(…)` with `type Choice = Tone | ""`) holds
the union's enum, and a lookup table it reads is a `match` over the variants. 0.11 held the string,
and the last arm of such a `match` stood for one member. The enum is written to `types.rs` for a
union of a `.ts` file and named after the component and the `ref` for one in place, so the
generated code holds more enums; the props, the island's JSON and Pinia state are unchanged.
