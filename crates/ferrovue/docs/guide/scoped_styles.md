`<style scoped>`: the `data-v-` attributes Vue's server renderer writes.

A component with `<style scoped>` has its CSS rewritten by the client build to select its own
elements only: `.tag { … }` becomes `.tag[data-v-7f092129] { … }`, and every element the
component's template renders carries `data-v-7f092129`. The server has to write the same attributes,
so the generated code writes them where Vue's server renderer does, and with the id the client build
chose.

# The id, and matching the client build

Vue's hydration does not compare attributes it does not need to patch, so a wrong id is no mismatch:
the page hydrates cleanly and its styles silently fail to apply. ferrovue therefore computes the id
as `@vitejs/plugin-vue` does, the first 8 hex digits of a SHA-256 of the `.vue` file's path from
Vite's root, followed by its source unless only the path is hashed, and the two must be configured
alike:

| `@vitejs/plugin-vue` | `ferrovue.config.json` |
|---|---|
| `vite build` with the default options | `"scopeId": "filepath-source"` (the default) |
| `features: { componentIdGenerator: "filepath" }` (any mode), or the dev server | `"scopeId": "filepath"` |

Set `viteRoot` too when Vite's root is not the directory holding `ferrovue.config.json`: it is that
root, relative to the configuration file, and the path that is hashed is the component's path from
it. The Vite plugin (`ferrovue/vite`) compares the two when a component has scoped styles: a build
in which they differ fails, and the dev server warns.

The default is the plugin's production behaviour, because the production build is the one readers
get: with every option left alone, its styles apply. But plugin-vue hashes the path alone in its dev
server, so with the default a page rendered during development carries other ids than the dev
client's and shows unstyled. The recommended setup hashes the path alone on both sides, as the
repository's `examples/fullstack` does:

```ts
// vite.config.ts
export default defineConfig({
  plugins: [vue({ features: { componentIdGenerator: "filepath" } }), ferrovue()],
});
```

```json
{ "components": "client/components", "out": "src/generated", "scopeId": "filepath" }
```

The ids are then the same in development and production, and neither they nor the generated Rust
change whenever a component's source does.

# What the generated code writes

The id goes on every element the component's template renders, after the element's own attributes.
A child component's root also carries the id of the scoped component that renders it, as Vue's

A component has a `render_scoped` when a parent may hand its root ids: when a scoped component
renders it, when it is the root of a component that may be handed ids itself, or when it sits in
slot content that may be given a slot scope id (below). `fv_attrs` holds those ids, each written
` data-v-…` with its leading space; [`scope_attrs`](crate::scope_attrs) puts them together in the
order Vue's `ssrRenderAttrs` writes them, keeping each once. Recursion, fragments, a root chosen by
`v-if`, `inheritAttrs: false`, `<Transition>`, `<KeepAlive>`, `<Teleport>` and `<RouterLink>` are
handled as Vue renders them. A component a parent also passes attributes to takes the ids inside an
[`Attrs`](crate::Attrs), after those attributes
([`generated_code`](crate::guide::generated_code#fallthrough-attributes)).

`render_scoped` is `#[doc(hidden)]`: call `render`. A component rendered from Rust, as a page's root
or an island, has no parent to hand it ids, and `render` writes exactly what Vue's server renderer
writes for the component mounted on its own. Markup you write yourself, in a slot closure or around
a component, carries only the ids it writes, so a component's scoped styles do not reach it.

# Slots and `:slotted()`

Slot content is the parent's markup, so it carries the parent's id only. A component
whose styles use `:slotted()`, `.note :slotted(p) { … }`, has them compiled to select
`data-v-…-s`, the slot scope id, and its outlets pass that id to the content they render, which
writes it onto its elements and hands it to the roots of components in it:

```vue
<!-- client/components/Note.vue -->
<script setup lang="ts">
defineProps<{ count: number }>();
</script>

<template>
  <aside class="note"><slot>no note</slot><footer><slot name="footer" :count="count" /></footer></aside>
</template>

<style scoped>
.note :slotted(p) { margin: 0; }
</style>
```

The outlets call [`slot_into_slotted`](crate::slot_into_slotted) and
[`scoped_slot_into_slotted`](crate::scoped_slot_into_slotted), the variants of
[`slot_into`](crate::slot_into) and [`scoped_slot_into`](crate::scoped_slot_into) that take the
slot scope id, and a scoped slot's closure takes the id as a third parameter:

```rust
# mod note {
# use ferrovue as fv;
# pub struct Props { pub count: i64 }
/// The props `<slot name="footer">` passes the content a parent gives it, borrowed for the render.

    pub count: i64,
}

/// A parent's content for `<slot name="footer">`, given its props and the slot scope id to write onto its elements: returns whether it wrote anything but comments.
pub type FooterSlot<'s> = dyn Fn(&mut String, &FooterSlotProps, &str) -> bool + 's;

/// What a parent puts in the slots `Note.vue` renders.
#[derive(Clone, Copy, Default)]

    /// `<slot>`
    pub default: Option<fv::Slot<'s>>,
    /// `<slot name="footer">`
    pub footer: Option<&'s FooterSlot<'s>>,
}

    out.reserve(84);
    out.push_str("<aside class=\"note\" data-v-421eaec8>");
    fv::slot_into_slotted(out, fv_slots.default, "data-v-421eaec8-s", Some(&mut |out: &mut String| {
        out.push_str("no note");

    out.push_str("<footer data-v-421eaec8>");
    fv::scoped_slot_into_slotted(out, fv_slots.footer, &FooterSlotProps { count: props.count }, "data-v-421eaec8-s", None);
    out.push_str("</footer></aside>");
}
# }
```

# Where Vue's server and client differ

Where Vue's own server render gives other ids than its client render, ferrovue writes the server's,
since the server's HTML is what it promises to match:

- a `:slotted()` component's slot fallback, which only the client gives the slot scope id;
- a component with `inheritAttrs: false` that is another component's root, whose root only the
  client gives the ids that other component inherits.

Hydration keeps the server's attributes in both cases, as it does for a page Vue rendered.

# What is refused

- `<style module>`, and `v-bind()` in CSS;
- `<RouterView>` in a component with `<style scoped>`, which would give the page that component's id;
- since vue-router renders a link from virtual nodes, a `<slot>` inside a `<RouterLink>` that takes
  scope ids, and an element inside a `<RouterLink>` in slot content given a `:slotted()` id.

A global `<style>` block, beside a scoped one or alone, needs nothing from the server.
