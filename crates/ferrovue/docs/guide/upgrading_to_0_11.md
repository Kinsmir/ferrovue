Upgrading a project from ferrovue 0.10 to 0.11: the steps to take, what behaves differently, and
what a component may now use.

The [CHANGELOG](https://github.com/Kinsmir/ferrovue/blob/main/CHANGELOG.md) lists every change;
this page picks out what an application notices. The page for the release before is
[`upgrading_to_0_10`](crate::guide::upgrading_to_0_10).

# Steps

## 1. Bump both halves together

The npm package and the crates are released together at one version, and generated code works with
the crate of its own release. Bump the npm package:

```sh
pnpm add -D ferrovue@^0.11.0
```

and the crate, in `Cargo.toml`:

```toml
ferrovue = "0.11"
```

`ferrovue` depends on `ferrovue-core`, `ferrovue-router` and `ferrovue-i18n` at exactly its own
version, so an application that names only `ferrovue` gets the other three with it. One that names
any of them itself bumps it to 0.11 as well.

The npm package needs Node 22.23.4 or newer on 22, 24.22.1 or newer on 24, or 26.12.1 or newer.

## 2. Generate every component again

```sh
pnpm ferrovue
```

The 0.11 compiler writes version 5 of generated code, and `mod.rs` opens with
`ferrovue::__compat!(5)`. Version 5 names what the 0.10 crate lacks:
[`ParseUnionError`](crate::ParseUnionError), the error of the enums below, the helpers that
write dates inside lists, dictionaries and interfaces, and [`Refused`](crate::Refused), the error
of a refusal at render time. The 0.11 crate
supports versions 2 to 5, so modules generated by 0.10 still build against it; generate them again
all the same. The 0.10 crate supports versions 2 to 4: given a module of version 5 it stops the
build at that line, with what to do:

```text
error: this module was generated as version 5 of ferrovue's generated code, and this `ferrovue` crate supports versions 2 to 4: use the `ferrovue` npm package and the `ferrovue` crate of one release, and run `ferrovue` to generate the module again
```

A CI job that runs `pnpm ferrovue --check` reports each module as stale until it is generated
again with 0.11 and committed. See [the version check](crate::guide::generated_code#the-version-check).

## 3. Build union props from their enums

A prop, or a field of an interface, typed as a union of two or more string literals is now a Rust
enum the compiler generates, where 0.10 made it a `Cow<'a, str>`. A string `enum` is one too. The
Rust that builds such props stops compiling at each place it passes a string, and changes as
follows:

```ts
// types/ui.ts
export type Size = "sm" | "md" | "lg";
```

```vue
<!-- Button.vue -->
<script setup lang="ts">
import type { Size } from "../types/ui";
defineProps<{ size: Size; tone?: "calm" | "loud"; label: string }>();
</script>
```

```rust
# mod generated {
# pub mod types {
#     #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, serde::Serialize, serde::Deserialize)]
#     pub enum Size {
#         #[serde(rename = "sm")]
#         Sm,
#         #[serde(rename = "md")]
#         Md,
#         #[serde(rename = "lg")]
#         Lg,
#     }
#     impl std::str::FromStr for Size {
#         type Err = ferrovue::ParseUnionError;
#         fn from_str(s: &str) -> Result<Self, Self::Err> {
#             match s {
#                 "sm" => Ok(Size::Sm),
#                 "md" => Ok(Size::Md),
#                 "lg" => Ok(Size::Lg),
#                 _ => Err(ferrovue::ParseUnionError::new("Size", s, &["sm", "md", "lg"])),
#             }
#         }
#     }
# }
# pub mod button {
#     use std::borrow::Cow;
#     #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, serde::Serialize, serde::Deserialize)]
#     pub enum ButtonTone {
#         #[serde(rename = "calm")]
#         Calm,
#         #[serde(rename = "loud")]
#         Loud,
#     }
#     pub struct Props<'a> {
#         pub size: super::types::Size,
#         pub tone: Option<ButtonTone>,
#         pub label: Cow<'a, str>,
#     }
#     impl<'a> Props<'a> {
#         pub fn new(size: super::types::Size, label: impl Into<Cow<'a, str>>) -> Self {
#             Props { size, tone: None, label: label.into() }
#         }
#         pub fn tone(mut self, tone: ButtonTone) -> Self {
#             self.tone = Some(tone);
#             self
#         }
#     }
# }
# }
# fn main() -> Result<(), ferrovue::ParseUnionError> {
use generated::{button, types::Size};

// 0.10: button::Props::new("md", "Save").tone("loud")
let props = button::Props::new(Size::Md, "Save").tone(button::ButtonTone::Loud);

// A string that arrives at run time, from a query, a form or a database, is parsed once.
let from_query = "lg";
let props = button::Props::new(from_query.parse::<Size>()?, "Save");
# assert_eq!(props.size, Size::Lg);
# Ok(())
# }
```

A union declared with a `type` alias, or a string `enum`, keeps its name (`Size`, in `types.rs` for
a `.ts` file); one written in place is named after its component and prop (`ButtonTone`), or its
interface and field. [Unions of string literals](crate::guide::props#unions-of-string-literals)
gives the naming of variants and the whole of the generated API: `as_str()`, `ALL`, `Display`,
`FromStr`, `TryFrom<&str>` and serde's names of the literals. Parsing a string outside the union
fails with [`ParseUnionError`](crate::ParseUnionError), and props that hold one in their JSON do not
deserialise, fixtures included: a conformance fixture with a value TypeScript would not allow
needs a member of the union.

A struct literal that set such a field to `"md".into()` or `Cow::Borrowed("md")` sets it to
`Size::Md`. A function of the application that took the field as a `&str` takes
`props.size.as_str()`.

The JSON of an island, `data-props` and the state sent to the page are unchanged: serde writes each
variant as its literal. 0.11 adds no configuration key that keeps the strings: the type error at
each place a string is passed names what to change.

## 4. Error codes your CI matches

These sources compiled with 0.10 and are refused with 0.11, as TypeScript refuses them:

| Source | 0.11 |
|---|---|
| `k === "z"` where `"z"` is not a member of `k`'s union | FV0637 |
| a literal outside a child's union prop (`size="xl"`), or a `string` handed to it | FV0515 |
| a `withDefaults` default outside its union | FV0322 |
| a constant list's field outside its interface's union | FV0215 |

And these unions have no enum to be:

| Source | 0.11 |
|---|---|
| a literal with no letter or digit (`"+" \| "-"`) | FV0323 |
| two literals that name one variant (`"md" \| "MD"`), or an `enum` with two members of one value | FV0324 |
| an enum named as another type of its module (`interface ButtonSize` beside `size: "sm" \| "md"` in `Button.vue`), two `.ts` files declaring different unions of one name, or a union called `Option` | FV0325 |

# Behaviour that changed

## Refusals at render time

Every component has a `try_render` beside its `render`, with the same parameters, returning
`Result<(), ferrovue::Refused>`, so a handler that renders props from a request answers props the
render cannot write as Vue writes them with `400 Bad Request`. See
[`errors_and_limits`](crate::guide::errors_and_limits#refused-at-render-time). Nothing that
compiled with 0.10 stops compiling, and nothing that rendered renders differently:

- `render`, `html`, `island`, `into_html` and `into_island` work as before, and
  [`Html::render_to`](crate::Html::render_to), [`Html::into_string`](crate::Html::into_string),
  [`Page::render_to`](crate::Page::render_to) and [`PageHole::fill`](crate::PageHole::fill) too.
  Each has a twin that returns the refusal: `try_render`,
  [`Html::try_render_to`](crate::Html::try_render_to),
  [`Html::try_into_string`](crate::Html::try_into_string),
  [`Page::try_render_to`](crate::Page::try_render_to) and
  [`PageHole::try_fill`](crate::PageHole::try_fill).
- What panicked as it rendered still panics where it is called without `try_`: a date string
  outside the format browsers read alike, `Date.UTC()` parts engines compute differently,
  `.toISOString()` of an invalid date, a `.repeat()` count JavaScript throws on, a date a chrono
  `Date` prop cannot hold. The message is the refusal's, `error[FV1803]:
  components/Published.vue:3:9: the date …`, where it was a message of its own: a test that
  expects the panic matches its code.
- An integer beyond ±2⁶³ that the template hands a child's `number` prop, uses as an index or
  counts a `v-for` with was cast to `i64` and rendered as `9223372036854775807`, which Vue does not
  write. It is refused now, with [FV0724](crate::guide::error_codes#fv0724): `render` panics on
  it, and `try_render` returns it.
- The generated `html()` of a component that takes slots or render parameters returns
  `Html<'p, Props, impl ferrovue::Renderer<Props>>` where it returned `impl Fn(&mut String,
  &Props)`. Code that renders it, or hands it to a [`Page`](crate::Page) or a
  [`Part`](crate::Part), is unchanged.

## Lookups and `<component :is>` over a union

A lookup table (`PAD[size]`) or `<component :is>` read by a value of a union's enum is a `match`
over its variants, each named, with no catch-all arm: a value outside the union cannot be built, so
no arm stands for one. A key the compiler holds as a string (a `computed` that builds it) and an
integer union keep the `_` arm, which reads the union's last member.

## Equality

`size === "md"` compiles to a comparison of variants, and `!==` too; `v-if` and `v-else-if`
chains and a `switch` over the value follow.

## FV1806 and dates inside the props

A `Date` inside a list, a dictionary or an interface of the props, and in a loader's result, which
0.10 refused with FV1806, now compiles. FV1806 refuses a `Date` only in Pinia state, `provide`,
`inject`, a typed `ref` and a `defineModel`; a list of lists of dates is FV1810, and a
dictionary of lists of dates FV0317. An island whose props hold such dates writes `data-dates`
beside `data-props`, a page's record writes `d` beside a part's `p` and `dates` beside the
layout's `props`, and the payload of loaders' results writes `dates`; the client of 0.11 reads
them, and an app that reads an island's props itself passes its `data-dates` to `reviveDates`.

# Newly supported

**Dates inside lists, dictionaries and interfaces**
([`dates_and_prices`](crate::guide::dates_and_prices#dates-inside-lists-and-objects)): a field
`at: Date`, `Date[]`, `(Date | null)[]`, `Record<string, Date>` and interfaces holding them, in
the props and in a loader's result, read in the template as a prop's date is and turned back into
`Date`s in the browser from a plan the compiler writes.

**Unions of string literals as enums** ([`props`](crate::guide::props#unions-of-string-literals)):
a `type` alias, a union in place, optional or nullable, and a string `enum`, generated once per
module, handed between components as the enum, converted to another union that holds its members,
and written in the page as its literal.
